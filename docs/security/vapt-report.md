### Round 2: parallel lanes (data-channel protocol v3)

Transfers now use up to 4 WebRTC connections ("lanes") with offset-tagged frames that are reordered on the receiver
(see [protocols.md](../protocols.md)). The new code went through an independent adversarial review with the same threat
model (malicious peer, malicious signaling server), then every finding was fixed and covered by a test.

| ID  | Sev.   | Finding                                                                                                                                                                | Fix                                                                                                                                                                                 | Verified by                                                                                        |
| --- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| H5  | High   | Lane connections had their own DTLS certificates, which the safety code doesn't cover: a malicious signaling server could answer lane offers itself and read file data | One certificate per session for **every** connection; a lane is used only if its remote fingerprint (from `getStats`) equals the main connection's, so the safety code covers lanes | Browser test: honest peers open 4 lanes; impostor certificates get all 6 lane connections rejected |
| M5  | Medium | Receiver buffer bound was per file: starting many files multiplied the memory a peer could pin                                                                         | One bound across all files: reorder + early frames + data waiting for the disk ≤ 2 × window, else the session stops                                                                 | `transfer-manager.test.js` "bounds buffered data across all files"                                 |
| M6  | Medium | Millions of 1-byte out-of-order frames looked tiny by byte count but cost far more memory                                                                              | Each held frame is charged 1 KiB of bookkeeping on top of its payload                                                                                                               | "many tiny out-of-order frames are charged"                                                        |
| M7  | Medium | A sender kept streaming (outside the window) after the receiver failed the file, and the row went back from Failed to Verifying                                        | Streaming stops when the file ends for any reason; finished rows can never become active again                                                                                      | "a sender stops streaming as soon as the receiver reports a failure"                               |
| M8  | Medium | `start` didn't re-check after its awaits: a cancel during it could revive the file                                                                                     | After each await: bail out if stopped, reconnected, cancelled or replaced                                                                                                           | Code review; existing cancel tests                                                                 |
| L9  | Low    | Messages queued from a dropped connection were still processed after the resync and could move offsets past what SYNC reported                                         | Inbox items carry the connection epoch; older ones are dropped (SYNC recovers everything they carried)                                                                              | Resume tests (single and multi-lane)                                                               |
| L10 | Low    | A lane refused or dropped on one side stayed open on the other, which kept sending frames nobody read                                                                  | Refused or dropped lanes are closed, so both sides resend                                                                                                                           | "a lane it refuses is closed"                                                                      |
| L11 | Low    | A retransmit loop exiting during a reconnect could strand records queued for the new connection                                                                        | The loop restarts itself when work remains                                                                                                                                          | Code review; "a lane dropping mid-transfer loses nothing"                                          |

Round 2 re-test (2026-11-07): `npm audit` 0 vulnerabilities, Trivy **0 at any severity** on all four images, active
suite **36/36**, 67/67 regression tests.

### Round 3: page reloads (2026-11-07)

Found while diagnosing a user report ("the approval prompt never came", then "that room already has two
devices" after reloading).

| ID  | Sev.   | Finding                                                                                                                                                  | Fix                                                                                                                                               | Verified by                                                                                              |
| --- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A1  | Medium | After the **sender** reloaded, its new page numbered files from slot 0 again, and the receiver ignored them as stale: later files never started          | Each page sends a random `instance` id in `sync`; a new id resets the receiver's slot tracking and fails the old page's files with a clear reason | `transfer-manager.test.js` "sender reloads"; browser test: the next file after a reload arrives verified |
| A2  | Medium | After the **receiver** reloaded, the sender kept streaming into a page that no longer knew the file, so the file hung forever                            | On a new instance id, unfinished outgoing files go back to "awaiting" and are offered again, so the approval prompt returns                       | "receiver reloads mid-transfer"; browser test (before and during the transfer)                           |
| A3  | Low    | A reload lost the seat token, so the room looked full ("already has two devices") for the 2-minute grace period, and retries spent the wrong-code budget | The seat is kept in `sessionStorage` (this tab only) and a reload rejoins automatically; clearer room-full message                                | Browser test: reload rejoins the same room and reconnects with 4 lanes                                   |
| A4  | Low    | When the engine stopped itself (incompatible version, protocol abuse) the UI still showed "Connected"                                                    | The engine emits `stopped` and the session ends with the reason on screen                                                                         | "tells the UI when it had to stop the session itself"                                                    |

The token in `sessionStorage` was assessed: per tab and per origin, cleared when the tab closes or the user
leaves, useful only while the server still holds the seat, and the strict CSP blocks injected scripts.

Round 3 re-test: `npm audit` 0, Trivy **0 at any severity** on all four images, active suite **36/36**, 70/70
regression tests.

### Round 4: Direct mode (desktop ↔ desktop over TCP, 2026-11-07)

The desktop app gained Direct mode: a TCP listener in the receiver's main process, a one-time 256-bit key handed over
the WebRTC data channel, AES-256-GCM frames, native file writes with the CLI's safe-write rules, and fallback to
WebRTC (see [security.md](../security.md#desktop-direct-mode) and
[protocols.md](../protocols.md#direct-mode-desktop--desktop-over-tcp)). The new code went through an independent
adversarial review. Threat model: an attacker anywhere on the LAN, a hostile peer controlling every `direct-*`
message and TCP frame, and a compromised renderer (untrusted by the main process). **No critical or high
findings.**

| ID  | Sev.              | Finding                                                                                                                                                                    | Fix                                                                                                                                                            | Verified by                                                                                    |
| --- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| D1  | Medium            | If the link dropped after the receiver saved a file but before the sender got `RESULT`, the sender's WebRTC fallback `start` was ignored and it waited forever             | A `start` for a file the receiver already finished gets its `progress` + `ack` repeated                                                                        | `transfer-manager.test.js` "a file resent after it was already saved gets its result repeated" |
| D2  | Low               | Slow-drip unauthenticated sockets could occupy the listener and block the real sender                                                                                      | Hard 10 s deadline (not an idle timeout), at most 8 pending with the **oldest evicted**, at most 2 per remote address; listener bound to IPv4 only             | `direct.test.js` "junk connections and garbage frames never get in"                            |
| D3  | Low               | A hostile peer could make our app dial chosen ports on loopback or anywhere on the LAN                                                                                     | Dial only addresses on our own subnets or a `100.64/10` overlay; loopback only when the receiver advertises one of our own addresses (same machine)            | "dials loopback only for a receiver on this machine…"                                          |
| D4  | Low               | Race on the open-native-files cap: parallel `openFile` calls could all pass the check before any finished                                                                  | The slot is reserved before the first await                                                                                                                    | Code review                                                                                    |
| D5  | Low               | Wrong `savedAs` for a folder at a drive root (`D:\`): slicing assumed an extra separator                                                                                   | `path.relative(root, savedPath)`                                                                                                                               | Code review                                                                                    |
| D6  | Low               | Orphaned `.hopline-part` files, or a hung abort, when a file was cancelled or the page reset during `open` or while waiting for `drain`                                    | Writer keeps an `aborted` flag checked after `open`; `drain` is raced with `close`; a reset generation makes work started before a reset clean up after itself | "the receiver can cancel mid-file…"; code review                                               |
| D7  | Low               | A disk error on the receiver (disk full, drive removed) looked like a lost link, so the file was resent over WebRTC into the same problem                                  | `SKIP` carries the error; the file fails with that reason and the link stays up                                                                                | Code review                                                                                    |
| D8  | Low               | Engine event listener leaked across sessions (each new `TransferManager` subscribed again)                                                                                 | `onEvent` returns an unsubscribe function, called when the manager stops                                                                                       | Code review                                                                                    |
| D9  | Low (speculative) | FAT/exFAT may report `EISDIR` for hard links, failing the no-overwrite commit; `COM¹`–`COM³`, `LPT¹`–`LPT³`, `CONIN$`, `CONOUT$` weren't treated as reserved Windows names | `EISDIR` added to the check-then-rename fallback in `safe-write.js`; the extra names added to `WINDOWS_RESERVED` (CLI and desktop share both)                  | `core.test.js` path safety; code review                                                        |

Accepted residual risks from this round (also listed below):

- `HELLO` isn't bound to the TCP connection. An on-path LAN attacker could replay a captured `HELLO` to take the
  listener's single slot. It learns nothing and can't forge later frames; the real sender can't connect and the file
  falls back to WebRTC.
- A cancel that arrives during the final commit may still leave the (complete, verified) file saved.
- The desktop installers are unsigned (SmartScreen / Gatekeeper warnings).
- `npm audit` (dev dependencies only) reports 6 moderate advisories for `minimatch` inside electron-builder (glob
  ReDoS, GHSA-g3hv-75wg-m249). electron-builder runs only at build time on our own glob patterns and isn't shipped
  in any app or image; forcing a patched major breaks electron-builder. `npm audit --omit=dev` is 0.

Round 4 re-test (2026-11-07): active suite **36/36**, Trivy **0 at any severity** on all four rebuilt images,
`npm audit --omit=dev` **0**, **90/90** automated tests. End to end: two packaged `Hopline.exe` instances moved
2 GiB over Direct mode in 17.5 s and the desktop app moved 10 GiB in 85.3 s, both SHA-256 identical.

### Live deployment test (Render, 2026-11-07)

The suite now accepts HTTPS targets. Against the public instance `https://hopline.onrender.com` (Render web
service behind Render's proxy): **21/21** applicable checks pass (HTTP headers, path traversal, methods, header
floods, WebSocket origin, `X-Forwarded-For` spoofing, message size and floods, malformed payloads, relay
credentials, room isolation, brute force, plus the local CLI checks; TURN and the all-in-one image don't apply).
Two hosting-proxy behaviours were accounted for, not weakened: closed WebSockets reach the server 10–25 s late,
so the per-client limit stays full briefly, and an oversized message's `1009` close reaches the client as a
`1006` drop. In both cases the server had already refused or closed the connection. A browser-to-browser
transfer through the live site (3 files, 40 MB) completed in 8.3 s, all SHA-256 verified.

## Accepted residual risks

| Risk                                                                                              | Rationale                                                                                      |
| ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| A malicious signaling server could attempt a WebRTC MITM                                          | Mitigated by the 16-digit safety code, which also covers the lanes; run your own server        |
| A sink write that never settles stalls the inbox                                                  | Browser storage APIs settle or throw in practice; cancelling or leaving still ends the session |
| 6-character room codes                                                                            | Throttled to 10 wrong guesses/min/client; one guest per room; safety code exposes impostors    |
| A LAN attacker can spend the 5 CLI guesses to stop a transfer                                     | Stopping is the safe failure; user retries                                                     |
| Fixed credentials from a managed TURN provider don't expire                                       | Prefer `TURN_SECRET`; documented                                                               |
| Memory storage fallback on old browsers / plain HTTP                                              | UI warns above 1 GB; HTTPS enables disk storage                                                |
| Direct mode `HELLO` can be replayed by an on-path LAN attacker to take the single connection slot | Nothing is exposed (no key, no plaintext); the file falls back to WebRTC                       |
| A cancel during a Direct file's final commit may still save it                                    | The file is complete and SHA-256 verified; the user can delete it                              |
| Unsigned desktop installers                                                                       | Download only from the project's GitHub Releases page; signing needs paid certificates         |

## Re-running

```bash
# 1. Start the stack (with the relay) and the all-in-one image
docker compose --profile turn up --build -d
docker run -d --name hopline-aio -p 8795:8787 hopline:all-in-one

# 2. Active tests (writes security/vapt/results.json)
node security/vapt/run.mjs

# 3. Image scan
docker run --rm -v //var/run/docker.sock:/var/run/docker.sock aquasec/trivy image --severity HIGH,CRITICAL hopline/web:latest

# 4. Dependencies and regression tests
npm audit
npm test
```

The active suite only attacks the hosts you point it at (`VAPT_WEB`, `VAPT_NODE`, `VAPT_TURN`). Run it only
against deployments you own.
